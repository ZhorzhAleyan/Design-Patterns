# SOLID սկզբունքները C++-ով

Այս repo-ն ցույց է տալիս **SOLID**-ի հինգ սկզբունքները կոնկրետ C++ օրինակներով։
Ամեն սկզբունքի համար կա երկու ֆայլ՝

- `bad.cpp` — սկզբունքը **խախտող** կոդ (ինչպես չանել)
- `good.cpp` — սկզբունքին **հետևող** կոդ (ինչպես անել ճիշտ)

SOLID-ը 5 սկզբունքների հավաքածու է՝ մաքուր, ընդլայնվող ու հեշտ պահպանվող
օբյեկտ-կողմնորոշված կոդ գրելու համար։ Հեղինակը՝ Robert C. Martin («Uncle Bob»)։

---

## Սկզբունքները

### 1. Single Responsibility Principle (SRP) — Մեկ պատասխանատվության սկզբունք
> Կլասը պիտի ունենա փոխվելու ընդամենը **մեկ** պատճառ։

Ամեն կլաս պիտի պատասխանատու լինի միայն մեկ բանի համար։ Եթե կլասը միաժամանակ
կառավարում է տվյալները, պահպանում բազայում ու ուղարկում email — դա շատ է։

📁 [`01_single_responsibility/`](01_single_responsibility/)

---

### 2. Open/Closed Principle (OCP) — Բաց/Փակ սկզբունք
> Կոդը պիտի լինի **բաց ընդլայնման** համար, բայց **փակ փոփոխման** համար։

Նոր ֆունկցիոնալ ավելացնելու համար պիտի կարողանաս գրել նոր կոդ, ոչ թե փոխել
արդեն աշխատող, փորձարկված հին կոդը։ Սովորաբար հասնում ենք աբստրակցիաների
(ինտերֆեյսների) միջոցով։

📁 [`02_open_closed/`](02_open_closed/)

---

### 3. Liskov Substitution Principle (LSP) — Լիսկովի փոխարինման սկզբունք
> Ենթակլասի օբյեկտները պիտի կարողանան **փոխարինել** բազային կլասի օբյեկտներին
> առանց ծրագրի ճիշտ աշխատանքը կոտրելու։

Եթե `Square`-ը ժառանգում է `Rectangle`-ից, բայց փոխում է վարքը այնպես, որ
Rectangle-ի հետ աշխատող ֆունկցիաները սկսում են սխալվել — LSP-ն խախտված է։

📁 [`03_liskov_substitution/`](03_liskov_substitution/)

---

### 4. Interface Segregation Principle (ISP) — Ինտերֆեյսների տարանջատման սկզբունք
> Հաճախորդը չպիտի ստիպված լինի կախված լինել մեթոդներից, որ չի օգտագործում։

Մեկ մեծ «գեր» ինտերֆեյսի փոխարեն ավելի լավ է ունենալ մի քանի փոքր, կոնկրետ
ինտերֆեյսներ։ Այդ դեպքում կլասը իրականացնում է միայն այն, ինչ իրեն պետք է։

📁 [`04_interface_segregation/`](04_interface_segregation/)

---

### 5. Dependency Inversion Principle (DIP) — Կախվածությունների շրջման սկզբունք
> Բարձր մակարդակի մոդուլները չպիտի կախված լինեն ցածր մակարդակի մոդուլներից։
> Երկուսն էլ պիտի կախված լինեն **աբստրակցիաներից**։

Կլասը պիտի կախված լինի ինտերֆեյսից, ոչ թե կոնկրետ իրականացումից։
Կախվածությունը սովորաբար ներարկվում է դրսից (*dependency injection*)։

📁 [`05_dependency_inversion/`](05_dependency_inversion/)

## Կոմպիլյացիա և գործարկում

Անհրաժեշտ է C++17 կոմպիլյատոր (g++ կամ clang++)։

Առանձին ֆայլ գործարկելու համար՝

```bash
g++ -std=c++17 -Wall 01_single_responsibility/good.cpp -o good
./good
```

Կամ օգտագործիր `Makefile`-ը՝ բոլորը միանգամից build անելու համար՝

```bash
make        # build անում է բոլոր օրինակները build/ պանակում
make run    # build անում ու գործարկում է բոլորը
make clean  # ջնջում է build/ պանակը
```
